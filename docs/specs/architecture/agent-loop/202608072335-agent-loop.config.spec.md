# Config: Loop do Agente

> Nenhuma variável de ambiente nova no código sem estar aqui.
> Precedência: flag > variável de ambiente > arquivo de config > default.

## 1. Limites do turno

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `HARNESS_MAX_ITERATIONS` | inteiro | `50` | Teto de iterações do loop. Dimensionado pelo caso legítimo: refactor cruzando dez arquivos consome de trinta a cinquenta chamadas de ferramenta. Abaixo de `20` quebra trabalho real e vira teto que o usuário desliga. É **backstop**, não o mecanismo principal. |
| `HARNESS_MAX_IDENTICAL_CALLS` | inteiro | `3` | Chamadas idênticas consecutivas — mesma ferramenta, mesmo input canonicalizado — que disparam `StopRepeatLoop`. É o mecanismo real: loop patológico aparece em três repetições, muito antes do teto de iterações. `0` desativa; só em depuração. |
| `HARNESS_MAX_TURN_TOKENS` | inteiro | `0` | Orçamento de token de saída por turno. `0` é ilimitado, e é o default **porque o teto de iterações já limita o gasto por construção**. Cortar por token no meio do turno deixa o workspace meio-editado — estado pior que o inicial. Defina apenas se precisar de controle duro de custo, aceitando esse risco. |

> Os três são defesa em profundidade e propositalmente redundantes. Se você precisa reduzir `HARNESS_MAX_ITERATIONS` para conter custo, o problema provavelmente é o detector de repetição desligado ou uma ferramenta devolvendo erro pouco informativo.

## 2. Execução de ferramentas

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `HARNESS_TOOL_PARALLELISM` | inteiro | `4` | Máximo de ferramentas executando ao mesmo tempo num passo. `1` serializa tudo — útil para depurar corrida. Acima de `8` o ganho satura e a pressão de memória por sessão cresce, o que ataca a tese da ADR-01. |
| `HARNESS_TOOL_TIMEOUT` | duração | `120s` | Timeout de uma execução individual. Estourar produz `ToolError` recuperável, não aborta o turno (RN-4). |
| `HARNESS_TOOL_PARALLEL_ENABLED` | booleano | `true` | Desligar força execução sequencial por `Index`. A ordem de anexação é idêntica nos dois modos — só a concorrência muda. |

## 3. Compactação

O gatilho e o formato vivem no motor de contexto (`202608072333-context-engine.config.spec.md`). O loop só configura a geração do resumo.

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `HARNESS_SUMMARY_MAX_TOKENS` | inteiro | `2000` | Teto do resumo gerado. Resumo longo demais anula o ganho da compactação; curto demais perde a tarefa corrente (RN-6 do motor de contexto). |
| `HARNESS_SUMMARY_MODEL` | string | vazio | Modelo usado só para resumir. Vazio usa o modelo da sessão. Modelo mais barato aqui é otimização legítima — o resumo não decide nada, só condensa. |

## 4. Medição de contratos comportamentais

A configuração de eval é transversal a todas as specs que têm contratos comportamentais, e por isso tem **dono único**: `202608072334-provider-adapter.config.spec.md`, seção 4.

`HARNESS_EVAL_MODEL`, `HARNESS_EVAL_RUNS` e `HARNESS_EVAL_ENABLED` são declaradas lá e valem também para os cenários da seção 7 do `.p` desta spec. Não redeclare aqui — duas declarações da mesma variável é ambiguidade de fonte da verdade, exatamente o que a regra do `.config` existe para impedir.

Trocar qualquer um desses valores **invalida os limiares desta spec também**, e exige nova medição.

## 5. Constantes não configuráveis

| Constante | Valor | Motivo |
|---|---|---|
| Ordem de anexação de resultado | por `Index` | Ordem por término tornaria o histórico irreprodutível e quebraria todo golden. |
| Serialização por conflito | sempre | Escrita concorrente no mesmo caminho é corrida, não otimização. |
| Passagem pelo avaliador de política | sempre | RN-7; caminho alternativo é blocker. |
| Texto da nota de execução concorrente | constante | Texto variável invalidaria o cache a cada passo (ADR-03). |
| Erro de ferramenta não aborta o turno | sempre | RN-4; abortar é o erro clássico de design de harness. |
| Chamada de resumo não conta iteração | sempre | É overhead do sistema, não trabalho do agente. |
