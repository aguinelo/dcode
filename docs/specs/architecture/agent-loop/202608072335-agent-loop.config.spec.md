# Config: Loop do Agente

> Nenhuma variável de ambiente nova no código sem estar aqui.
> Precedência: flag > variável de ambiente > arquivo de config > default.

## 1. Limites do turno

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `DCODE_MAX_ITERATIONS` | inteiro | **da família** | Teto de iterações do loop. `0` ou ausente usa o default declarado pela família em uso (RN-9 do provider): `minimax-m3` → `2000`, `claude` → `50`. Um número global serviria mal aos dois: 50 foi dimensionado por um refactor cruzando dez arquivos, e M3 é treinado para horizonte longo. É **backstop**, não o mecanismo principal. |
| `DCODE_MAX_IDENTICAL_CALLS` | inteiro | `3` | Chamadas idênticas consecutivas — mesma ferramenta, mesmo input canonicalizado — que disparam `StopRepeatLoop`. É o mecanismo real: loop patológico aparece em três repetições, muito antes do teto de iterações. `0` desativa; só em depuração. |
| `DCODE_MAX_TURN_TOKENS` | inteiro | `0` | Orçamento de token de saída por turno. `0` é ilimitado, e é o default **porque o teto de iterações já limita o gasto por construção**. Cortar por token no meio do turno deixa o workspace meio-editado — estado pior que o inicial. Defina apenas se precisar de controle duro de custo, aceitando esse risco. |

> O teto vem da família porque o horizonte de trabalho é propriedade do modelo, não do harness. Ver `202608072334-provider-adapter`, seção 2.1.

> Os três são defesa em profundidade e propositalmente redundantes. Se você precisa reduzir `DCODE_MAX_ITERATIONS` para conter custo, o problema provavelmente é o detector de repetição desligado ou uma ferramenta devolvendo erro pouco informativo.

## 1.1 Definição de pronto (RN-10)

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `DCODE_DONE_FILE` | caminho | `<workspace>/.dcode/done.toml` | Onde a definição de pronto é declarada. Fica sob `.dcode/`, que a `DefaultRules` já submete a confirmação de escrita — um agente que edita a própria definição de pronto amplia o próprio alcance. |
| `DCODE_DONE_ENABLED` | booleano | `true` | Liga a reentrada por critério pendente. Desligar devolve o comportamento antigo: o turno termina quando o modelo para de chamar ferramenta, cumprido ou não. |
| `DCODE_MAX_STALL_CYCLES` | inteiro | `2` | Ciclos sem progresso antes de encerrar em `StopIncomplete`. Dois porque o caso legítimo existe — um ciclo para diagnosticar, outro para corrigir. Três já é o modelo girando. |
| `DCODE_DONE_TIMEOUT` | duração | `10m` | Teto por critério. Critério que não termina não é critério, e travar o turno é pior que relatar o estouro. |

> **Não há chave para tornar a saída incondicional.** "Não sair até estar 100%" cria o incentivo de enfraquecer o medidor: se a saída é teste verde e o agente não consegue, o caminho mais curto é apagar a asserção. A saída é por **progresso** justamente para que esse caminho nunca seja o mais curto.

## 1.2 Delegação (RN-11)

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `DCODE_DELEGATE_ENABLED` | booleano | `true` | Liga a ferramenta de delegação. Desligar remove-a do registro; nenhum outro comportamento muda. |
| `DCODE_DELEGATE_MAX_ITERATIONS` | inteiro | `100` | Teto do turno filho. Continua menor que o do pai: o filho faz **um** pedaço de trabalho, e um que precisa de centenas de rodadas é um pedaço que devia ter sido dividido. Era `20`, dimensionado quando o filho só respondia pergunta — um filho que lê um pacote e escreve uma nota faz mais que responder, e 20 trunca isso antes de começar. |
| `DCODE_DELEGATE_MAX_RESULT_BYTES` | inteiro | `32768` | Teto do relatório devolvido. Excedido, trunca e **declara**. O teto é sobre a **resposta**, não sobre o trabalho: filho que devolve o próprio contexto derruba o propósito, porque o custo da leitura volta pela porta da resposta. |

> **Não há chave para delegar com escrita, para aninhar, nem para o filho pedir aprovação.** As três são estruturais: o modo é fixado na construção, o registro do filho não contém a própria ferramenta, e o aprovador não é passado adiante. Chave que afrouxasse qualquer uma delas seria a ADR-02 desligada por configuração.

## 2. Execução de ferramentas

| Variável | Tipo | Default | Uso |
|---|---|---|---|
| `DCODE_TOOL_PARALLELISM` | inteiro | `4` | Máximo de ferramentas executando ao mesmo tempo num passo. `1` serializa tudo — útil para depurar corrida. Acima de `8` o ganho satura e a pressão de memória por sessão cresce, o que ataca a tese da ADR-01. |

## 4. Medição de contratos comportamentais

A configuração de eval é transversal a todas as specs que têm contratos comportamentais, e por isso tem **dono único**: `202608072334-provider-adapter.config.spec.md`, seção 4.

`DCODE_EVAL_MODEL`, `DCODE_EVAL_RUNS` e `DCODE_EVAL_ENABLED` são declaradas lá e valem também para os cenários da seção 7 do `.p` desta spec. Não redeclare aqui — duas declarações da mesma variável é ambiguidade de fonte da verdade, exatamente o que a regra do `.config` existe para impedir.

Trocar qualquer um desses valores **invalida os limiares desta spec também**, e exige nova medição.

## 5. Constantes não configuráveis

| Constante | Valor | Motivo |
|---|---|---|
| Ordem de anexação de resultado | por `Index` | Ordem por término tornaria o histórico irreprodutível e quebraria todo golden. |
| Serialização por conflito | sempre | Escrita concorrente no mesmo caminho é corrida, não otimização. |
| Passagem pelo avaliador de política | sempre | RN-7; caminho alternativo é blocker. |
| Texto da nota de execução concorrente | constante | Texto variável invalidaria o cache a cada passo (ADR-03). |
| Erro de ferramenta não aborta o turno | sempre | RN-4; abortar é o erro clássico de design de harness. |
| Chamada de resumo não conta iteração | sempre | É overhead do sistema, não trabalho do agente. |
| Turno delegado em `ModeReadOnly` | sempre | RN-11; é o que faz três dos quatro problemas de delegação não existirem. |
| Turno delegado não pede aprovação | sempre | ADR-02; consentimento dado ao pai não vale para o filho. |
| Filho não delega | sempre | RN-11; custo exponencial e erro longe da causa. |
| Tokens do filho debitados do pai | sempre | RN-11; senão o teto do pai é ficção. |
| Critério de pronto é comando com código de saída | sempre | RN-10; critério julgado pelo modelo devolve ao modelo a decisão de pronto. |
| Progresso é encolhimento estrito do conjunto de pendentes | sempre | RN-10; qualquer medida mais frouxa é satisfeita por esforço que não produz resultado. |
| `StopIncomplete` não é erro | sempre | RN-10; virando erro, a saída fácil passa a ser desligar a checagem. |
| Mudança em caminho protegido nunca conta como progresso em silêncio | sempre | RN-10; é a linha entre garantir qualidade e fabricar a aparência dela. |
| Skill não declara critério cumprido | **nunca** | RN-10; seria o caminho de menor resistência para sair do laço. |
