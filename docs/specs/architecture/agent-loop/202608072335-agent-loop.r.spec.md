# Research: Loop do Agente

> Fonte da verdade de negócio para o ciclo que transforma uma instrução do usuário em trabalho executado.
> Depende de: **ADR-02** (sandbox), **ADR-03** (contexto append-only), **ADR-04** (client-server), **ADR-05** (provider).

## 1. Contexto

O loop é o coração do dcode. Ele orquestra motor de contexto, adaptador de provider, ferramentas e sandbox — todos os outros componentes existem para servi-lo.

É também onde o produto ganha ou perde caráter. Um loop que aborta ao primeiro erro de ferramenta produz um agente frágil. Um loop sem teto produz um agente caro. Um loop que executa ferramenta fora da fronteira produz um agente perigoso.

## 2. Fronteira de determinismo

**Regime: misto.** Esta é a spec onde a linha realmente importa.

| Parte | Regime | Verificação |
|---|---|---|
| Máquina de estados do turno | determinístico | asserção |
| Teto de iterações e detector de repetição | determinístico | asserção |
| Ordem de anexação de resultados | determinístico | golden file |
| Semântica de interrupção | determinístico | asserção |
| Gatilho e aplicação de compactação | determinístico | asserção |
| **Recuperação após erro de ferramenta** | **mediado por modelo** | limiar |
| **Encerramento do turno na hora certa** | **mediado por modelo** | limiar |

A mecânica é toda determinística. O que é mediado é **o que o modelo decide fazer** dentro dela.

## 4. Regras de negócio

### RN-1 — O turno é um ciclo até não haver mais ferramenta a chamar
```
1. anexa entrada do usuário ao histórico
2. monta contexto            ← ponto de checagem de compactação
3. streaming do provider
4. sem tool call? → turno completo · FIM
5. executa as tool calls, anexa resultados
6. incrementa iteração; estourou teto? → turno termina em erro
7. volta ao 2
```

### RN-2 — Dois limites, com papéis diferentes
**Teto de iterações** é backstop, dimensionado pelo caso legítimo: um refactor cruzando dez arquivos consome de trinta a cinquenta chamadas de ferramenta. Teto que quebra trabalho real vira teto que o usuário desliga.

**Detector de repetição** é o mecanismo real: N chamadas idênticas consecutivas — mesma ferramenta, mesmo input — indicam loop patológico e travam muito antes do teto.

A identidade é sobre o **input**, não sobre a ferramenta. Isso é o que faz o detector conviver com RN-4: tentar de novo com abordagem diferente não é chamada idêntica.

O teto de tokens existe como controle de custo, mas **não é a defesa primária** — cortar por token no meio do turno deixa o workspace meio-editado, estado pior que o inicial. O teto de iterações já limita o gasto por construção.

### RN-3 — Ferramentas executam em paralelo; a ordem não é sequencial perfeita
Tool calls independentes de um mesmo passo executam concorrentemente.

Três consequências obrigatórias:

1. **Anexação em ordem determinística**, pelo índice em que o modelo as emitiu — nunca pela ordem de término. É o que mantém o histórico reproduzível e golden-testável.
2. **O modelo é informado** de que a execução foi concorrente e que os resultados não refletem ordem temporal. Ele não pode assumir que a ferramenta 1 terminou antes de a 2 começar.
3. **O log registra a ordem real** — início e fim de cada execução — para que a depuração enxergue o que a anexação esconde.

**Conflito serializa.** Chamadas que tocam o mesmo caminho de arquivo, ou que executam comando de sistema, não correm em paralelo entre si. Paralelismo vale para leitura e busca, onde é seguro e onde está o ganho real.

### RN-4 — Erro de ferramenta alimenta o modelo, nunca aborta o turno
O resultado do erro é anexado como resultado de ferramenta e o loop continua. O modelo reanalisa e decide: seguir mesmo assim, repetir, tentar caminho alternativo — inclusive por comando de sistema — ou desistir e relatar.

Para essa decisão ser possível, o erro precisa ser **informativo**: o que foi tentado, o que falhou, e o sinal disponível. Uma string genérica força o modelo a adivinhar, e adivinhar é como um agente corrompe arquivo.

Abortar o turno ao primeiro erro é o erro clássico de design de harness. O modelo quase sempre se recupera sozinho, e recuperar é justamente o que se espera de um agente.

### RN-5 — Interrupção é possível em todo ponto de espera
O usuário interrompe entre passos, durante o streaming e durante a execução de ferramenta. O turno encerra com estado consistente: nenhuma escrita pela metade, nenhum resultado órfão no histórico.

Ferramenta já iniciada quando a interrupção chega **termina** ou é cancelada, mas seu resultado é anexado de qualquer forma se ela produziu efeito. Histórico que mente sobre o que aconteceu no disco é pior que histórico incompleto.

### RN-6 — Compactação é verificada uma vez por iteração, no passo 2
Só ali. Verificar em outro ponto convida a compactação incremental, que a ADR-03 proíbe.

Gerar o texto do resumo é chamada ao modelo e pertence ao loop, não ao motor de contexto — é o que mantém aquele componente puro.

### RN-7 — Toda ferramenta passa pela política antes de executar
Sem exceção e sem caminho alternativo. Execução direta que contorne o avaliador de política é blocker imediato.

Cruzar a fronteira bloqueia o turno e pede aprovação; sem resposta no prazo, **nega** — falha fechada, conforme a spec do protocolo.

### RN-8 — Todo fato observável vira evento antes de qualquer outra coisa
O loop não escreve em terminal nem em arquivo de log como caminho primário: ele emite evento. Quem exibe é o cliente.

É o que sustenta a ADR-04 — a mesma sessão observada por TUI, IDE ou nenhum cliente se comporta de forma idêntica.

## 5. Fora de escopo

- Implementação das ferramentas — spec própria.
- Fronteira do sandbox e sua aplicação pelo sistema operacional — spec própria.
- Sub-agentes, delegação e execução paralela de múltiplos turnos.
- Retomada de turno após queda do servidor.
