# Research: Conjunto de Ferramentas

> Fonte da verdade de negócio para as ferramentas que o agente usa para ler e modificar o projeto.
> Depende de: **ADR-02** (sandbox), **ADR-03** (contexto append-only).

## 1. Contexto

É o que torna o produto um **agente de codificação** e não um chat. Sem ferramentas, o modelo descreve mudanças; com elas, faz.

O estudo comparativo identificou o design de ferramentas como a maior força do Claude Code, e a ferramenta de edição como o ponto mais crítico do conjunto: substituição por string exata com invariante de leitura prévia é mais confiável que diff/patch e muito mais barata que reescrita completa.

Este componente também é onde um agente corrompe arquivo do usuário, se estiver errado. É o de maior consequência por linha de código.

## 2. Fronteira de determinismo

**Regime: determinístico.**

Toda ferramenta é função de entrada e estado do sistema de arquivos. Não há mediação por modelo dentro delas — o modelo decide *qual* chamar e *com quê*, mas isso pertence ao loop.

**Consequência para a revisão:** tudo aqui é verificável por asserção contra sistema de arquivos real em diretório temporário. O `.p.spec.md` não tem seção de contratos comportamentais.

## 4. Regras de negócio

### RN-1 — Conjunto mínimo do MVP
Seis ferramentas: **`read`**, **`write`**, **`edit`**, **`glob`**, **`grep`**, **`bash`**.

`glob` e `grep` são tecnicamente dispensáveis — `bash` faz os dois. Existem mesmo assim por duas razões: são muito mais baratas em token que capturar saída de comando, e permitem granularidade de permissão que `bash` não permite. Busca é leitura; não deveria passar pelo mesmo escrutínio de executar comando arbitrário.

### RN-2 — Ferramenta dedicada vence shell
Toda operação com ferramenta dedicada disponível usa a ferramenta, não `bash`. Isso não é preferência de estilo: `bash` é o caminho de maior privilégio, e usá-lo para ler arquivo desperdiça permissão e token.

### RN-3 — Invariante read-before-edit
**`edit` só opera em arquivo lido nesta sessão, e não modificado desde a leitura.**

A sessão rastreia o que foi lido e um hash do conteúdo naquele momento. `edit` falha se:
- o arquivo nunca foi lido nesta sessão; ou
- o conteúdo mudou desde a leitura.

É a regra que impede a falha mais cara do produto: editar às cegas um arquivo cujo conteúdo o modelo supôs. Sem ela, o agente sobrescreve trabalho do usuário feito em paralelo — silenciosamente.

O erro é informativo o bastante para o modelo se recuperar: relê e tenta de novo.

### RN-4 — Match ambíguo falha, nunca adivinha
`edit` substitui por string exata. Se o trecho aparece mais de uma vez, a operação **falha** informando quantas ocorrências existem.

Escolher a primeira ocorrência é o comportamento tentador e é errado: acerta na maioria das vezes e, quando erra, edita silenciosamente o lugar errado. Falha explícita é sempre melhor que acerto probabilístico quando o custo do erro é corromper código.

### RN-5 — Saída é limitada, e o truncamento é declarado
Nenhuma ferramenta devolve saída ilimitada. Ao truncar, o resultado **diz** que truncou e quanto sobrou.

Truncar em silêncio faz o modelo concluir sobre dados que não viu — e concluir com confiança, porque nada indicou o corte.

### RN-6 — Toda ferramenta passa pela política
Sem exceção, incluindo leitura. Quem decide é o avaliador do componente de sandbox e política; a ferramenta só declara quais caminhos toca e se usa rede.

### RN-7 — Saída de ferramenta nunca é volátil sem necessidade
O resultado entra no contexto append-only. Timestamp, duração e caminho absoluto que varie por máquina não entram, salvo quando são a informação pedida.

Uma ferramenta que injete o horário em toda saída invalida o cache a cada chamada.

### RN-8 — `write` cria; `edit` modifica
`write` é para arquivo novo ou substituição integral consciente. Sobrescrever arquivo existente com `write` exige que ele tenha sido lido — mesma invariante de RN-3, porque o risco é o mesmo.
