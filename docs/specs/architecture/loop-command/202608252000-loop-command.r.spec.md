# Research: Comando /loop

> Fonte da verdade de negócio para a fachada que traduz uma especificação externa
> em `DoneSet` para o ciclo do agente. Depende de: **`202608072335-agent-loop`**
> (RN-10 e a mecânica de `Criterion`/`DoneSet`/`Progressed`), **`202608091700`**
> (regras por caminho, em particular `DefaultRules` que submete `.dcode/**` a
> confirmação), **`202608072240-client-server-protocol`** (a interface pela qual
> o comando chega).

## 1. Contexto

O dcode já sabe **executar** um turno contra uma `DoneSet` e **parar por
progresso** quando os critérios encolhem. O que ele **não sabe** é aceitar uma
descrição de trabalho vinda de fora — uma pasta `specs/2026-08-25-home-page/`
com `spec.md` e `tasks.md`, por exemplo — e transformá-la em `DoneSet` na hora de
começar o turno.

> **Estado, 2026-08-26.** Nada no produto chama esta família. O que existe é o
> parser, o dispatch entre fontes e o `loop.Config` que a sessão dedicada vai
> receber. O reconhecimento de `/loop` no cliente é o Passo 3 da `.i` e **não
> foi construído** — `/loop` ainda não é digitável. As regras abaixo são o que
> a família vai fazer; a `.p §5` e a `.i` dizem, passo a passo, o que já faz.

`/loop` é a fachada que preenche essa lacuna. **Não é uma máquina nova**: é uma
forma de declarar intenção que produz o mesmo `DoneSet` que `done.toml` já
produz, lido de uma fonte diferente. O ciclo que consome é o mesmo, as
invariantes que o guardam são as mesmas, o orçamento é o mesmo. O que muda é
só a **origem dos critérios**.

O caso de uso que motivou isto é a pipeline da plataforma Code Plain
(`dreibox/codeplain`), onde 16 specs vivem em `specs/` no formato
`spec.md` + `tasks.md` e a sequência de execução é bloco-a-bloco contra
critérios verificáveis (`pnpm test:coverage ≥ 80%`, `Lighthouse ≥ 95`, etc.).
Sem `/loop`, "implementar a spec X" exige o usuário traduzir manualmente
`tasks.md` em `done.toml` toda vez; com `/loop`, o harness lê a pasta e produz
a `DoneSet` direto.

## 2. Fronteira de determinismo

**Regime: misto.** A parte que decide o que rodar é determinística; a parte que
decide **o que fazer quando o critério falha** é mediada pelo modelo e já está
coberta pela `agent-loop` (RN-10 e o contrato comportamental
`fixes-cause-not-measure`).

| Parte | Regime | Verificação |
|---|---|---|
| Reconhecimento do comando `/loop` no input do usuário | determinístico | asserção |
| Resolução do caminho da spec no filesystem | determinístico | asserção |
| Parsing de `tasks.md` em `[]Criterion` | determinístico | golden file |
| Extração de `Protected` declarado pelo usuário | determinístico | asserção |
| Construção da `DoneSet` final | determinístico | asserção |
| Criação de sessão dedicada com a `DoneSet` | determinístico | asserção |
| **Execução** do turno contra a `DoneSet` | já existe | já tem invariantes |
| **Como** o agente cumpre cada critério | já existe (mediado) | já tem limiar |

A linha de demarcação é a mesma que aparece em
`SDD-HARNESS.md §3`: "pushing behavior to the deterministic side is a design
goal". O parser **não pode** interpretar prosa — converteria critério em
julgamento do modelo, que é exatamente o que a `agent-loop` RN-10 proíbe. Prosa
existe na spec para o **humano** ler; o harness só consome a parte estruturada
(`tasks.md`).

## 3. User stories

| # | Como | Quero | Para |
|---|---|---|---|
| US-1 | operador | digitar `/loop specs/2026-08-25-home-page/` e ver o agente executar bloco a bloco | não ter que traduzir `tasks.md` em `done.toml` a cada spec |
| US-2 | operador | digitar `/loop implemente absolutamente todas as specs` e ver o agente iterar sobre as 16 specs da plataforma | começar o trabalho do dia com um comando, não com 16 linhas de configuração |
| US-3 | operador | que `/loop` crie uma sessão nova, não polua a sessão atual | isolar o trabalho por spec, manter a sessão interativa livre |
| US-4 | operador | que a `DoneSet` carregada por `/loop` respeite o `Protected` que eu declarei | não deixar o agente enfraquecer os próprios testes |
| US-5 | operador | que o parser reclame de `tasks.md` malformado em vez de inventar | ver erro claro, não `DoneSet` vazia que termina em `StopDone` |

## 4. Regras de negócio

### RN-1 — `/loop` é uma fachada, não uma máquina nova

A `DoneSet` que `/loop` produz é do mesmo tipo que `done.toml` produz
(`loop.DoneSet`). O ciclo que a consome é o mesmo (`loop.Engine`), os
`StopReason` são os mesmos, o relatório é o mesmo. Nenhum código novo no
`internal/loop/` é necessário para executar o turno — só para **alimentar a
`DoneSet`**.

Isto é deliberado: a `agent-loop` tem invariantes verificáveis
(`agent-loop.p §8`) que guardam o ciclo. Reescrevê-lo para "otimizar o caso
`/loop`" reintroduz cada uma dessas invariantes por outra porta.

### RN-2 — Sessão nova, sempre

`/loop` **não** muta a sessão interativa corrente. Cria uma sessão dedicada
com nome derivado do caminho da spec (`loop-{basename}-{timestamp}`),
executa o turno lá, encerra. A sessão interativa continua disponível para
comandos avulsos.

Justificativa: o trabalho de uma spec é unidade autocontida. Misturar com a
sessão viva cria dois problemas concretos — (a) a `DoneSet` da sessão
interativa (legado: `.dcode/done.toml`, ou o `verifyCommand` quando ele não
existe) acumula com a da spec e a RN-10 vira
progresso contra um conjunto não pretendido; (b) o usuário perde o canal
para interromper a spec sem matar o que mais estava fazendo.

### RN-3 — Reconhecimento no cliente, não no turno

O comando `/loop` é reconhecido **antes** de virar entrada de turno. O client
(TUI ou daemon) intercepta o prefixo, traduz o argumento em uma chamada
`LoopSpec{Path}`, e popula `Config.Done` da nova sessão. O texto `/loop ...`
em si **não** vira mensagem no histórico — gasta zero tokens da janela com
sintaxe.

Justificativa: mesma regra da `agent-loop` §3 — empurrar comportamento pro
lado determinístico. Sintaxe de comando entrando pro histórico é estado
variável no prefixo, o que invalida o cache de prefixo a cada turno
(ADR-03). O reconhecimento no cliente também casa com o que o `GO-CODE-REVIEW`
chama de "Tabela de mensagens: o cliente exibe, o loop emite" — o comando é
uma das formas de o cliente falar com o loop.

### RN-4 — `Protected` é declaração, nunca inferência

Os caminhos que o agente **não pode** modificar em silêncio são declarados
pelo usuário, não inferidos pela posição da spec. O dcode **não** trata
`specs/**` como `Protected` por default só porque o `/loop` carregou dali.
Conhecimento de "isto é medição" é do operador, não do harness.

A forma da declaração é decisão de formato do `tasks.md` da plataforma
consumidora (Code Plain, ou outro) — não desta spec. O dcode aceita o
`Protected` que veio no argumento ou no arquivo, sem prescrever onde fica.

### RN-5 — Prosa não vira critério

O parser consome **apenas** a parte estruturada de `tasks.md` (a lista de
tarefas com caminho e comando esperado, quando houver). Texto narrativo
("smoke manual", "verificar com o usuário") vira `CriterionUnavailable` no
relatório — exatamente como comando vazio já vira na `agent-loop`
(`done_test.go:104`). Prosa existe para humanos; o harness só lida com o que
pode **executar**.

### RN-6 — `tasks.md` que não dá para ler é erro, não `DoneSet` vazia

A `DoneSet` resultante é vazia **apenas** quando o `tasks.md` declara zero
critérios explicitamente — isto é, quando ele **tem tarefas** e nenhuma delas
traz comando. Um arquivo sem nenhuma linha de tarefa não está declarando nada:
o parser não o entendeu, e **retorna erro**.

A distinção é a regra inteira. "Não há o que verificar" e "não consegui ler"
produzem a mesma `DoneSet` vazia, e `DoneSet` vazia é "sem definição de
pronto", que o ciclo relata como **pronto**. Sem separar as duas, o arquivo que
ninguém conseguiu ler vira o relatório verde — que é o pior resultado que esta
família pode produzir, e o motivo desta RN existir.

Pelo mesmo motivo, o que é **sintaxe** é o mínimo: `- [ ] N.` e
`verify: \`cmd\``. Pontuação entre os dois não é contrato. A primeira
implementação exigia travessão literal e devolvia zero critérios, sem erro,
para todo `tasks.md` escrito com hífen.

### RN-8 — Objetivo sem pasta nenhuma é qualificado, não recusado

`/loop <frase>` foi construído para **escolher** entre pastas de spec, e quando não havia nenhuma ele recusava: *"no specs/ folder here, or nothing in it. /loop `<path>` works on one folder."* — o comando dizendo a alguém que o pedido dele era da forma errada.

Isso contradizia a família ao lado. A `done-qualifier` existe exatamente para o pedido em prosa, e a `.r` dela nomeia esse caso como o que a motivou: *"Faça um cadastro de clientes"* não traz `tasks.md` nenhum, e a resposta construtiva é levantar os critérios, medi-los e pedir assinatura. O caminho `/loop <caminho>` já fazia isso quando a pasta não declarava nada; só o caminho da frase morria antes.

Objetivo em prosa que não encontra pasta alguma abre a **sessão de qualificação** sobre a própria frase. Ela é o briefing inteiro, então é ela que o turno nomeia — e o turno não manda ler especificação que não existe, porque procurar uma gasta as rodadas que ele tem.

A proposta é ancorada em `.dcode`, que é onde a definição de pronto de um workspace já mora e é uma das três origens de `DoneSet`. **Não** numa pasta derivada da frase: a RN-5 registra o defeito oposto — prosa virando caminho, quando `/loop implemente todas as specs pendentes` foi procurar `implemente/tasks.md` — e inventar `revise-o-projeto/` seria o mesmo defeito de chapéu trocado.

`.dcode` é o único diretório que a escrita da proposta cria. Caminho de spec que não existe continua sendo erro: pasta digitada errada respondida com pasta criada é o silêncio que esta família recusa em todo lugar.

### RN-7 — Comando explícito "todas as specs" expande, não engloba

`/loop implemente absolutamente todas as specs` é uma forma abreviada de
iterar sobre o conjunto descoberto (no Code Plain, o diretório `specs/`). A
expansão produz **N sessões dedicadas** (RN-2), uma por spec, executadas em
sequência. Cada sessão tem sua própria `DoneSet`, seu próprio orçamento, seu
próprio relatório.

A expansão é determinística (listar diretórios, ordenar por timestamp do nome)
e o sequenciamento é do **operador**, não do agente. O operador pode
interromper entre specs sem perder trabalho das specs já concluídas.

## 5. Fora de escopo

- Escrita em `tasks.md` (marcar checkboxes) — é trabalho do agente, não do
  parser. O parser lê, não escreve.
- Indexação cross-spec ("spec A depende de spec B") — pipelines
  sofisticadas. Aqui cada spec é independente; dependências, quando houver,
  viram ordem de invocação no comando do operador.
- Suporte a formatos de spec diferentes de `spec.md` + `tasks.md` (ex.:
  OpenAPI, RFCs em prosa pura). YAGNI até alguém precisar.
- `DoneSet` carregada de URL remoto ou git. A spec é local. Pipeline remota
  é trabalho de outra camada.
- Compressão ou agregação de relatórios entre specs. Cada sessão tem seu
  relatório; juntar é trabalho do operador.
