# Implementing: Comando /loop

> Siga a ordem. Se algum passo contradisser o `.r.spec.md`, **pare** — o `.r`
> tem precedência. Todo código novo nasce de teste que falhou primeiro
> (`docs/conventions/TESTING.pt-BR.md`).

## Onde isto está, hoje

| Passo | Estado |
|---|---|
| 1 — `LoadSpec` | **feito** |
| 2 — `Load` (dispatch) | **feito** |
| 3 — reconhecimento do `/loop` no cliente | **feito** — o cliente reconhece `/loop` e manda o argumento ao daemon (`POST /v1/loops`) |
| 4 — configuração da sessão dedicada | **feito por outro caminho**: o `Runner` do daemon abre a sessão de cada pasta com o caminho da spec, e o daemon lê. `SessionConfig`, que nunca teve chamador, saiu |
| 5 — congelar o formato do `tasks.md` no Code Plain | **não feito** — gate de processo, bloqueia `stable` |
| 6 — contratos comportamentais | **sem objeto**: os quatro IDs da `.p §7` descrevem o parser, e o parser é asserção. O que o modelo faz com a `DoneSet` que recebe é da `agent-loop`, que já mede. |
| 7 — invariantes | **feito** para o que existe (`.p §8`), via `specguard` |

**O daemon conduz o `/loop`; a TUI e o desktop seguem** (changelogs
`202610141200` e `202610141700`). O cliente reconhece o comando e manda o
argumento como foi digitado; o `Runner` lê a gramática, pergunta às pastas,
qualifica, espera a revisão, abre uma sessão por pasta e dá o veredito; os
clientes seguem o fluxo de loops (`GET /v1/loops/events`) e dizem o que mudou.
A sessão é criada pelo daemon a partir do caminho da spec em vez de por um
`loop.Config` montado no cliente — o cliente pode não estar perto do disco, e
um cliente que lesse a spec estaria afirmando o que um arquivo que ele não
enxerga contém. Por isso `SessionConfig`, que montava esse `Config`, saiu sem
nunca ter tido chamador (changelog `202610161200`).

## Pré-requisitos

| Componente | Estado mínimo |
|---|---|
| `202608072335-agent-loop` | Passos 6 e 6.5 concluídos — `Engine`, `DoneSet`, `Criterion`, `Progressed`, `StopIncomplete` disponíveis |
| `202608091700-regras-por-caminho-e-comando` | `DefaultRules` disponível — `protected` em `.dcode/**` é o que mantém o agente de editar a própria `DoneSet` |
| `202608072240-client-server-protocol` | As rotas de loop — `POST /v1/loops`, `GET /v1/loops`, `continue`, `stop` e o fluxo `GET /v1/loops/events`. Não há evento de sessão de loop: a sessão que o loop abre chega no próprio `LoopRun`, pasta a pasta |

Pré-requisito externo (do **Code Plain**, não deste repo): o formato `tasks.md`
com a marcação `verify: \`...\`` precisa estar congelado. Mudar a forma do
`tasks.md` **depois** desta spec entrar em `stable` é mudança de contrato entre
repositórios e exige coordenação em changelog dos dois lados.

## Ordem de execução

### Passo 1 — `LoadSpec`, sem I/O além da leitura do arquivo

`internal/loop/loopcommand/loopspec.go`

- [ ] Tipo `LoopSpec` da seção 3 do `.p`.
- [ ] `LoadSpec(path string) (LoopSpec, error)`.
- [ ] `LoadSpecWithProtect(path string, protect []string) (LoopSpec, error)`.
- [ ] Frontmatter YAML entre `---` no topo de `tasks.md`. Falha de parsing é
      `error`, nunca `LoopSpec{}`.
- [ ] Cada `- [ ] N. \`path\` — desc. verify: \`cmd\`` vira
      `Criterion{Name: "N", Command: cmd, ExitCode: 0}`. Ordem preservada.
- [ ] `verify: \`cmd\`, exit: K` vira `Criterion{ExitCode: K}`.
- [ ] Tarefa sem `verify:` é **ignorada pelo parser** — não vira critério.
      Aparece no relatório final como `CriterionUnavailable` via mecânica já
      existente da `agent-loop` (comando vazio → `unavailable`).
- [ ] Tarefa `- [x]` é tratada igual a `- [ ]`: a marcação é trabalho do
      agente, não do parser.

**Testes obrigatórios:**

- Golden file da `tasks.md` real do Code Plain (`specs/2026-08-25-home-page/tasks.md`)
  produz a `LoopSpec` esperada byte-a-byte.
- `tasks.md` com 0 critérios → `LoopSpec{Criteria: nil, ...}`, **não** erro.
- `tasks.md` malformado (linha sem `---` antes do frontmatter, frontmatter no
  meio do arquivo) → erro com mensagem apontando a linha.
- Ordem dos critérios na `[]Criterion` casa com ordem de aparição.
- `LoadSpecWithProtect` com glob em conflito: arquivo-declarado vence, sem erro.
- `Criterion.Name` é `"N"` (o número da tarefa), não o path. Path fica no
  relatório via campo `Name` expandido se necessário, ou em log — não no tipo.

### Passo 2 — `Load` (dispatch entre fontes)

`internal/loop/loopcommand/dispatch.go`

- [ ] Tipo `Source` da seção 4 do `.p`.
- [ ] `Load(workspace, specPath string, src Source, verifyCommand string) (loop.DoneSet, error)`.
- [ ] `SourceAuto`: `done.toml` se existe, `LoopSpec` em `specPath` se setado,
      senão `DoneSet{verifyCommand}` (legado preservado).
- [ ] `SourceDoneFile` falha se `done.toml` ausente — não cai pra legado.
- [ ] `SourceLoopSpec` falha se `specPath` vazio ou pasta ausente.

**Testes obrigatórios:**

- `SourceAuto` com `done.toml` presente: `DoneSet` vem de `done.toml`,
  `specPath` ignorado.
- `SourceAuto` sem `done.toml`, com `specPath` válido: `DoneSet` vem de
  `LoopSpec`.
- `SourceAuto` sem nenhum dos dois: `DoneSet{verifyCommand}`.
- `SourceLoopSpec` com `specPath=""`: erro explícito.
- `Load` é determinístico — duas chamadas com mesmos args retornam `DoneSet`
  `reflect.DeepEqual`.

### Passo 3 — Reconhecimento do comando no client

`internal/tui/loop.go` (o cliente), `internal/loop/loopcommand/args.go` (a
gramática, no daemon), `internal/server/loops.go` (as rotas)

- [x] Input que casa `^/loop(\s|$)` não vira mensagem do turno: a TUI o manda
      ao daemon (`POST /v1/loops`), como foi digitado.
- [x] Argumento após `/loop` é dividido em: `specPath` e `--protect ...`.
      Qualquer outra flag é erro — não há flag de limite; os limites vêm da
      família e da configuração (`.p` §6). A TUI confere a gramática só para
      dizer o erro de digitação no idioma da pessoa; quem decide é o daemon.
- [x] Resolver `specPath` (absoluto ou relativo ao workspace) — no daemon.
- [x] Chamar `Load` e propagar erro com mensagem amigável ao usuário — no
      daemon, ao abrir a sessão da pasta.

**Testes obrigatórios:**

- Input `/loop specs/foo/` → nenhum conteúdo vai pro histórico da sessão
  interativa; uma sessão nova é criada com `DoneSet` da spec.
- Input `/loop` sem argumento → erro de uso visível no client.
- Input `/loop specs/foo/ --protect '**/*_test.go'` → `Protected` da sessão
  nova inclui o glob.
- Argumento desconhecido (ex.: `--foo`) → erro de uso, nada é criado.

> O client é onde o `/loop` é reconhecido, não o loop. **Implementação errada
> comum:** o texto `/loop ...` vira mensagem de turno e o loop filtra. Isso
> gasta tokens da janela com sintaxe e invalida o cache de prefixo. A regra é
> na RN-3 do `.r` e aqui vira asserção.

### Passo 4 — Sessão dedicada

Feito por outro caminho, e não neste pacote. O `Runner` pede a sessão ao
daemon com o caminho da pasta, e o daemon monta o `Config` como o de qualquer
sessão: a `DoneSet` vem de `LoadSpecWithProtect`, os limites da família e da
configuração. `SessionOptions` e `SessionConfig(opts) (loop.Config, string)`,
que montavam esse `Config` no cliente, saíram sem nunca terem tido chamador —
e os testes deles com eles (changelog `202610161200`).

**Invariantes do desenho antigo, que o `Runner` não seguiu.** Estavam na
`.p §8` reivindicadas por testes que não existiam, quando a sessão dedicada
seria montada no cliente. A máquina que existe hoje é outra — o `Runner` do
daemon —, e o que ela de fato garante está na `.p §8`, com teste. Estas ficam
registradas como desenho, não como dívida: a sessão de uma pasta **não** é
encerrada depois do turno — ela fica na lista, com o log, e o loop guarda qual
é de qual pasta —, e as outras são propriedades da sessão comum do daemon, que
o loop usa sem caminho próprio (RN-1):

- `NewSession` (o de verdade, o que fala com o servidor) chama o servidor
  **uma** vez por invocação.
- A sessão criada tem ID distinto de qualquer sessão pré-existente.
- A sessão é encerrada após o turno, mesmo em `StopInterrupted`/`StopError` —
  não vira sessão zumbi.
- Mudança em `Protected` durante o turno é destacada no relatório
  (`TouchedProtected`), nunca contada como progresso em silêncio.
- `Config.RunCriterion` é o `criterionRunner` do `internal/app/done.go` — não-nil
  e igual ao injetado, para que comandos de critério passem pelo sandbox.

Não entra aqui, e não entra em lugar nenhum: "`Progressed` é chamado entre
ciclos". Não há caminho novo a guardar. A `DoneSet` é um valor e o motor não
sabe de onde ela veio — é o que a RN-1 quer dizer com fachada. A `agent-loop`
já guarda o caminho que existe, em `TestNoProgressEndsTheTurnAsIncomplete`.

### Passo 5 — Fixar o formato do `tasks.md`

**Antes deste passo**, abrir uma issue/PR no **Code Plain** confirmando:

- [ ] Formato `verify: \`cmd\`` e `verify: \`cmd\`, exit: K` é o que a spec
      do Code Plain declara.
- [ ] `protected` no frontmatter é o mecanismo que o Code Plain adota (vs.
      `--protect` na linha de comando, vs. nenhum).

Sem esta confirmação, o Passo 1 do **Code Plain** pode mudar o formato e o
nosso parser fica falando com fantasma. Esta é a única dependência
cross-repo que existe.

**Não é código nosso** — é gate de processo. Se o Code Plain não congela o
formato, esta spec não passa de `experimental` para `stable`.

### Passo 7 — Invariantes

`internal/loop/invariants_test.go`

- [x] Um teste por linha da seção 8 do `.p`, verificado por
      `specguard.Check` em `internal/loop/invariants_test.go`
      (`TestEveryLoopCommandInvariantHasATest`). O glob do specguard só
      alcança `internal/*/invariants_test.go` — um nível —, então um arquivo
      de guarda dentro de `loopcommand/` nunca seria lido.
- [x] `go test -race ./internal/loop/loopcommand/...` limpo.
- [x] Cobertura ≥ 90% no próprio pacote, que é o piso que morde.

> **A armadilha deste passo, porque ela já foi pisada.** A primeira versão
> reivindicou a família com um teste que montava um mapa e nunca o lia, e
> comparava uma constante consigo mesma. Ele existia para o `strings.Contains`
> do specguard encontrar o nome da família num arquivo, e não podia falhar.
> Um guard que uma string satisfaz é um guard que uma string vai satisfazer:
> o que vale é rodar o `specguard.Check`, que lê cada linha da `.p §8` e
> reprova quando o teste nomeado não existe.

## Ordem de dependência

```
Passo 1 (LoadSpec)            ← puro, testável isolado
   └─ Passo 2 (Load)             ← dispatch entre fontes
        ├─ Passo 3 (client)       ← reconhecimento do /loop
        └─ Passo 4 (sessão)       ← o daemon monta o Config da sessão dedicada
             └─ Passo 6 (evals)      ← mede o comportamento
                  └─ Passo 7 (invariantes)
```

Passo 5 (fixar formato no Code Plain) é **bloqueante** dos Passos 1, 6 e 7.
Sem ele, parser e fixtures estão escrevendo contra formato não congelado.

## Marco executável

Ao fim do Passo 4, com `/loop specs/2026-08-25-home-page/` digitável num
workspace Code Plain real, o dcode executa **um** turno contra a `DoneSet`
extraída do `tasks.md`. É o marco desta spec, e foi atingido: o `/loop` é
digitável desde o `202608270300`, e o daemon o conduz desde o
`202610141200`.

Passo 5 é o que destrava `experimental → stable`.

## Armadilhas conhecidas

- **Parser interpretar prosa como critério** — violaria `agent-loop` RN-10
  literalmente. Prose vira `unavailable`, nunca `Criterion{Name: "smoke"}`.
- **`/loop` virar mensagem de turno** — invalida cache de prefixo a cada
  turno (ADR-03) e gasta tokens com sintaxe. Reconhecimento é no client,
  sempre.
- **Frontmatter `protected` inferido da posição da spec** — é exatamente o
  que a RN-4 da `.r` desta spec proíbe. `Protected` é declaração, não
  inferência.
- **Critério `- [x]` (já marcado) ser pulado pelo parser** — confunde
  "trabalho feito" com "trabalho conferido". A marcação é do agente, a
  verificação é do harness.
- **Sessão dedicada acumular com sessão interativa** — duas `DoneSet`
  coexistindo na mesma janela de progresso. Sessão nova, sempre.
- **Pontuação virando sintaxe** — o parser exigiu travessão literal entre o
  número da tarefa e a descrição. Um `tasks.md` escrito com hífen devolvia zero
  critérios e nenhum erro, e zero critérios é "sem definição de pronto", que o
  ciclo relata como pronto. Só `- [ ] N.` e `verify: \`cmd\`` são contrato.
- **Linha que não casa virando silêncio** — `continue` em tudo que o parser não
  reconhece transforma arquivo ilegível em relatório verde. Sem linha de tarefa
  nenhuma, é erro. RN-6.
- **`os.IsNotExist` sobre erro embrulhado** — ele não segue cadeia de `%w`, e
  com isso o fall-through de `SourceAuto` para o comando legado virou código
  inalcançável sob um comentário dizendo que era alcançável. `errors.Is`.
- **`DoneEnabled=false` quando há critérios** — desliga a reentrada por
  critério pendente e transforma `/loop` num turno comum com `verifyCommand`.
  Quebra a RN-10 sem aviso.
- **`StopIncomplete` virando erro** — a saída fácil vira desligar a
  checagem. Já documentado na `agent-loop`, mas esta spec herda o risco.
