# Planning: Comando /loop

> Contrato técnico. Use **EXATAMENTE** os nomes, campos e tipos definidos aqui.
> Regra de negócio em `202608252000-loop-command.r.spec.md`. O ciclo que consome
> a `DoneSet` produzida por este contrato está em `202608072335-agent-loop.p`.

## 1. Nível de estabilidade

**`experimental`.** Vive em `internal/loop/loopcommand` (novo subdiretório,
não no `loop/` raiz — a separação é deliberada e justificada na seção 2).
Não é superfície pública: o que é público é o protocolo
(`202608072240-client-server-protocol`), e `/loop` se expressa por ele.

**Nada no produto chama este pacote.** O reconhecimento de `/loop` no cliente
é o Passo 3 da `.i` e não foi construído: o que existe é o parser, o dispatch
entre fontes e o `loop.Config` que o chamador futuro vai passar. Enquanto isso
não muda, `/loop` não é digitável.

Promoção para `stable` requer, nesta ordem: o Passo 3 (o comando existir),
um contrato comportamental medido contra modelo real quando houver
comportamento a medir, e uma spec consumidora real (Code Plain) rodando em
produção por ≥ 1 release.

## 2. Onde mora o código

```
internal/loop/loopcommand/
    loopspec.go       # tipo LoopSpec, parser de tasks.md → []Criterion
    loopspec_test.go  # TDD: golden files + casos de borda
    dispatch.go       # seleção entre done.toml e LoopSpec
    dispatch_test.go
    session.go        # monta o loop.Config da sessão dedicada
    session_test.go
```

Sem `testdata/`: cada teste escreve o `tasks.md` que exercita em um
`t.TempDir()`. Uma fixture compartilhada entre vinte casos de borda vira o
arquivo que ninguém pode mudar sem quebrar dezenove testes que não são sobre
ela.

**Por que em `internal/loop/loopcommand/` e não em `internal/app/`.** O
`internal/app/done.go` carrega `done.toml`. Estender ali quebraria a
separação entre **carregar `DoneSet`** (que o `app/` faz) e **definir
`DoneSet` a partir de formato externo** (que é o que esta spec faz). A
fronteira natural é: o `loopcommand` produz `loop.DoneSet`; o `app/`
decide se usa `done.toml` ou delega ao `loopcommand`.

## 3. Tipo `LoopSpec`

```go
// Package: internal/loop/loopcommand

// LoopSpec is a parsed specification external to the workspace.
//
// The parser is total: it never panics on malformed input and never invents
// data. What it CANNOT read, it refuses to read — a file with no task list is
// an error, not an empty DoneSet. The difference matters more than it looks:
// an empty DoneSet is "nothing to verify", which the agent loop reports as
// done.
type LoopSpec struct {
    // Path is the directory containing spec.md and tasks.md.
    // The parser does not require spec.md to exist; tasks.md is the source
    // of truth for criteria. spec.md is for the human reader.
    Path string

    // Criteria are the verifiable conditions of done for this spec.
    // Sourced exclusively from tasks.md. Prose is not a source.
    Criteria []loop.Criterion

    // Protected are paths the agent may not modify silently during execution.
    // Sourced from the user, not inferred from where the spec lives.
    Protected []string
}
```

### 3.1 Parsing de `tasks.md`

Formato consumido (declaração do Code Plain — **esta spec do dcode não
prescreve o formato, só consome o que vem**):

```markdown
# Tasks — <nome>

## Bloco 1 — <título>

- [ ] 1. `path/arquivo.ts` — descrição.
       verify: `pnpm test:coverage`
- [ ] 2. `path/arquivo2.ts` — descrição.

## Bloco 2 — <título>

- [ ] 3. ...
```

Regras de parsing:

| Entrada | Saída |
|---|---|
| `- [ ] N. <qualquer coisa> verify: \`cmd\`` | `Criterion{Name: "N", Command: "cmd", ExitCode: 0}` |
| `- [ ] N. ... verify: \`cmd\`, exit: K` | `Criterion{...ExitCode: K}` |
| `- [ ] N. ... verify: \`cmd\` <prosa>` | `Criterion{...}`; a prosa depois do comando é do humano |
| `- [ ] N. ...` (sem `verify:`) | a tarefa é ignorada pelo parser; aparece no relatório como `CriterionUnavailable` |
| `- [x] N. ...` (já marcada) | idem — a tarefa existe, mas a verificação **ainda** precisa rodar; o agente é quem marca após critério cumprido |
| Linha que não é tarefa (título, prosa, branco) | ignorada; não é erro |
| `verify:` sem comando entre crases | **erro**, nomeando a linha |
| comando entre crases vazio | **erro**, nomeando a linha |
| cauda que menciona `exit` e não lê como `, exit: K` | **erro**, nomeando a linha |
| mesmo `N` declarado duas vezes | **erro**, nomeando as duas linhas |
| arquivo **sem nenhuma linha de tarefa** | **erro** — RN-6 |
| tarefas presentes, nenhuma com `verify:` | `LoopSpec{Criteria: nil}`, **não** erro |

**O separador não é sintaxe.** Entre o número da tarefa e o `verify:` o parser
não lê nada: travessão, meia-risca, hífen, dois-pontos, caminho entre crases ou
nada disso. Só o `- [ ] N.` e o `verify: \`cmd\`` são contrato.

A primeira versão exigia travessão literal (`—`). Um `tasks.md` escrito com
hífen — que é o que o teclado produz — devolvia zero critérios e nenhum erro, e
zero critérios é "sem definição de pronto", que o ciclo relata como pronto.
Pontuação virando contrato deixou a família a uma tecla de um verde falso.

**Frontmatter só abre na linha 1.** `---` no meio do arquivo é régua horizontal
do markdown, não delimitador. Tratá-lo como abertura engolia todas as linhas
seguintes, ou reprovava o arquivo inteiro como "frontmatter não fechado".

A ordem dos critérios no `[]Criterion` é a ordem de aparição no `tasks.md`
(que é a ordem de execução declarada). `Progressed` da `agent-loop` é
insensível à ordem, então isto é cosmético — mas a ordem de impressão no
relatório é humana, e humano lê em ordem.

### 3.2 `Protected`

`Protected` vem de **uma** destas duas fontes, na ordem:

1. Frontmatter `protected = [...]` no topo de `tasks.md` (entre `---`), se
   existir.
2. Argumento `--protect <glob>` na invocação do comando.

Se nenhum dos dois, `Protected` é vazio. **Não há default.** Esta é a
materialização da RN-4 da `.r`: o harness **não** decide o que é medição.

As duas fontes são **união**, não precedência, e a lista final não repete. Dizer
que "o arquivo vence o argumento" abriria a única direção que não pode existir
por acidente: um argumento **removendo** uma proteção que o arquivo pediu.
`Protected` não proíbe nada — ele destaca no relatório —, então unir é sempre
seguro e escolher nunca é.

```go
// LoadSpec reads a LoopSpec from a path. Returns an error on malformed input.
func LoadSpec(path string) (LoopSpec, error)

// LoadSpecWithProtect reads a LoopSpec and adds the argument's globs to those
// declared in the file. Union, not precedence; no duplicates.
func LoadSpecWithProtect(path string, protect []string) (LoopSpec, error)
```

## 4. Dispatch entre fontes

```go
// Source declares where a DoneSet comes from.
type Source int

const (
    SourceAuto    Source = iota // done.toml if present, else verifyCommand
    SourceDoneFile              // always done.toml
    SourceLoopSpec              // always LoopSpec
)

// Load resolves the source and returns the DoneSet.
// Pure: no I/O beyond reading the file once. Same file path can be queried
// repeatedly and returns the same value.
func Load(workspace, specPath string, src Source, verifyCommand string) (loop.DoneSet, error)
```

Comportamento de `SourceAuto` (preservado, idêntico ao atual):

| Existe `done.toml`? | Existe spec em `specPath`? | Resultado |
|---|---|---|
| sim | (ignorado) | `DoneSet` de `done.toml` |
| não | sim, e legível | `DoneSet` de LoopSpec |
| não | sim, e **ilegível** | erro — não cai no legado |
| não | não | `DoneSet{verifyCommand}` (legado) |

"Não está lá" e "está lá e não dá para ler" são respostas diferentes. Cair no
legado sobre uma spec ilegível rodaria o comando antigo enquanto o usuário
acredita que a spec foi carregada.

O `Load` desembrulha com `errors.Is(err, fs.ErrNotExist)`. Com `os.IsNotExist`,
que não segue cadeia embrulhada com `%w`, toda spec ausente voltava como erro
duro e a linha do meio desta tabela era código inalcançável sob um comentário
dizendo que era alcançável.

## 5. Configuração da sessão dedicada

> **Estado.** Esta seção descreve o que **existe**. Criar a sessão, rodar o
> turno e encerrá-la depois é do chamador, que é o Passo 3 da `.i` e **não
> foi construído**. O que dá para construir sem cliente é o `loop.Config` que
> esse chamador vai passar.

```go
// SessionOptions configures the dedicated session /loop will create.
type SessionOptions struct {
    Spec          LoopSpec
    Limits        loop.Limits
    MaxStall      int           // forwarded to Config.MaxStallCycles
    DoneTimeout   time.Duration // forwarded to Config.DoneTimeout
    SandboxMode   policy.SandboxMode
    Workspace     string
    Model         string
    SessionPrefix string
}

// SessionConfig builds the loop.Config a /loop session is born with, and the
// name that session will carry. It creates nothing.
func SessionConfig(opts SessionOptions) (loop.Config, string)
```

**Por que não se chama `NewSession`.** Chamava. A assinatura declarada aqui era
`NewSession(ctx, srv, opts) (SessionHandle, error)` — uma chamada que alcança o
servidor, devolve um handle com `ID()` e `SubmitTurn()` e é dona do ciclo de
vida da sessão. Nada disso existe, nem existia quando a `.p` foi escrita. Um
construtor que não constrói é o tipo de nome em que se confia uma vez.

O nome da sessão é `<prefix><basename(spec)>-<YYYYMMDDHHMMSS>`. Ele **não é
único**: a granularidade é de segundo, e duas invocações no mesmo segundo
colidem. Ele existe para um humano distinguir duas execuções na lista, e é isso
que a invariante afirma — a versão anterior afirmava unicidade, que era falsa
deste código.

**Por que sessão dedicada e não turno com `Done` mutado.** A `DoneSet` é
propriedade da **sessão**, não do turno — `loadDoneSet` é chamado uma vez,
quando a sessão nasce. Alterar `Done` mid-session viola o pressuposto de
que a definição de pronto é o que o usuário viu quando começou. RN-2 da
`.r` explica.

## 6. Limites

`/loop` aceita os mesmos limites da `agent-loop` (`Limits{}`), expostos
como flags do comando:

| Flag | Default | Origem |
|---|---|---|
| `--max-iterations` | 50 (família) | `loop.DefaultLimits().withFamily(50)` |
| `--max-identical` | 3 | `loop.DefaultLimits().MaxIdenticalCalls` |
| `--max-tokens` | 0 (sem teto) | `loop.DefaultLimits().MaxTurnTokens` |
| `--max-stall` | 2 | `Config.MaxStallCycles` |
| `--done-timeout` | 30s | `Config.DoneTimeout` |

Defaults no `.config.spec.md` da mesma família.

## 7. Contratos comportamentais

> Seção presente porque o `.r` classifica o escopo como misto. Os quatro
> contratos abaixo, porém, **não são medidos contra modelo** — são
> estabelecidos por asserção, e cada linha nomeia quais.

| ID | Cenário | Comportamento esperado | Limiar | Fixture |
|---|---|---|---|---|
| `loop-parses-spec` | `tasks.md` bem-formado | a `DoneSet` é a do golden, na ordem do arquivo | **100%** | `testdata/evals/loop-parses-spec/` |
| `loop-ignores-prose` | `tasks.md` mistura critério verificável e "smoke manual" | apenas o verificável vira `Criterion` | **100%** | `testdata/evals/loop-ignores-prose/` |
| `loop-protect-declared` | `tasks.md` declara `protected` | `Protected` é o declarado, unido ao argumento | **100%** | `testdata/evals/loop-protect-declared/` |
| `loop-protect-absent` | `tasks.md` sem `protected` declarado | nenhum caminho é protegido | **100%** | `testdata/evals/loop-protect-absent/` |

**Por que 100% é legítimo, e por que nenhum deles gasta uma chamada de modelo.**
O que os quatro descrevem é o parser, e o parser é determinístico. Medir contra
modelo gastaria vinte chamadas para imprimir `MET` a 100% sem olhar o
transcript — um verde de graça, que é o pior resultado possível porque ninguém
olha um verde duas vezes. Eles ficam na tabela porque **são** contratos
declarados; o que muda é quem responde por eles.

A versão anterior desta seção declarava os quatro como mediados, com limiares
de 99% e 95%, e as fixtures traziam `task.md` de placeholder porque a
ferramenta que o modelo usaria não existe. Ao mesmo tempo, o `.config` afirmava
que os limiares "**foram medidos**". Não foram: nenhuma medição jamais rodou.

**Quando esta seção volta a ter contrato mediado.** Quando o Passo 3 da `.i`
existir e o modelo puder invocar `/loop`. Aí há comportamento a medir — o que o
agente faz com a `DoneSet` que recebeu —, e aí a medição é escrita, rodada, e o
número registrado com modelo e data.

## 8. Invariantes verificáveis
- Objetivo em prosa que não acha pasta de spec alguma abre sessão de **qualificação**, e nunca recusa (RN-8).
- A proposta de um objetivo é ancorada em `.dcode`, e nunca em pasta derivada da frase (RN-8).
- O turno de qualificação de um objetivo **nomeia a frase** e não manda ler especificação inexistente (RN-8).
- Objetivo que acha pastas continua desenhando o plano e trabalhando as pendentes (RN-8).
- Palavra solta que não nomeia pasta encontrada alguma vira **objetivo qualificado**, e não caminho (RN-9).
- Argumento com separador que não existe continua sendo **erro**: qualificar um caminho digitado errado esconderia o erro (RN-9).

> Cada linha nomeia um teste que existe, e o `specguard` reprova quando um
> nome some. Uma invariante sobre máquina que não foi construída não entra
> aqui — ela está na `.i`, junto do passo que a constrói.

- `LoadSpec` retorna erro (não panic) para `tasks.md` malformado.
- Arquivo sem nenhuma linha de tarefa é erro, nunca `DoneSet` vazia — RN-6.
- Tarefas presentes e nenhuma com `verify:` é declaração de zero critérios, não erro.
- O separador entre o número da tarefa e o `verify:` não é sintaxe.
- `verify:` sem comando entre crases é erro que nomeia a linha.
- Cauda que menciona `exit` e não lê como `, exit: K` é erro, nunca zero silencioso.
- O mesmo número de tarefa duas vezes é erro.
- `---` fora da linha 1 é régua do markdown, nunca frontmatter.
- `LoopSpec.Criteria` preserva a ordem de aparição em `tasks.md`.
- Tarefa `- [x]` vira critério igual a `- [ ]`.
- `Protected` é a união do declarado no arquivo e do que veio por argumento.
- A mesma glob vinda das duas fontes aparece uma vez só.
- Sem declaração, nenhum caminho é protegido por posição — RN-4.
- `Load` com `SourceLoopSpec` ignora a presença de `done.toml`.
- `Load` com `SourceDoneFile` ignora a presença de `specPath`.
- `SourceAuto` com spec ausente cai no `verifyCommand` legado.
- `SourceAuto` com spec presente e ilegível é erro, nunca fall-through.
- `Load` é determinístico: mesmos argumentos, mesma `DoneSet`.
- `SessionConfig` produz `Config.Done` igual ao `DoneSet` da `LoopSpec`.
- `Config.DoneEnabled` é `true` se e só se há ao menos um critério.
- O nome da sessão carrega prefixo, basename e instante em UTC.
- Os limites chegam ao `Config` sem alteração: a fachada não tem orçamento próprio.

- Um `done.toml` na pasta da spec é a definição de pronto dela, e vence o `tasks.md`.
- `done.toml` de spec que não declara critério é erro, nunca queda para o `tasks.md`.
- Ausência de `done.toml` na pasta cai no `tasks.md` e não é erro.
- Argumento com separador, ou uma palavra só, é caminho; frase é objetivo.
- `/loop <objetivo>` descobre as pastas de spec, mostra o plano e roda **uma sessão por spec**, em ordem.
- "Pendente" é decidido **rodando** os critérios da pasta, nunca contando marcações.
- Pasta sem critério nenhum é pendente: ausência de prova não é prova de pronto.
- Pasta com `spec.md` e sem tarefas é pendente, não ilegível.
- Critério indisponível conta como trabalho restante.
- O plano lista **todas** as pastas, não só as pendentes.
- Descoberta é ordenada por nome, e cancelada devolve o que já tinha.
- A fila da spec seguinte só anda depois da fila digitada pela pessoa.
- `/loop` pergunta o que a pasta declara **antes** de abrir sessão, e a pergunta não roda critério nenhum.
- Pasta que não declara critério é qualificada antes de ser trabalhada.
- Survey que falha não impede o comando: ele abre a sessão e segue.
- O que a pessoa digitou **não** entra no turno qualificador.
- Depois de gravar a proposta o laço **para** e passa para a próxima spec, sem emendar no trabalho.
- `/loop` **submete um turno**: abrir a sessão e esperar é metade do trabalho.
- Palavra depois do caminho é o que fazer, não flag mistecleada; só o que começa com `-` pode ser flag errada.
- O que a pessoa escreveu vence o texto padrão, inteiro.
- O turno padrão nomeia a spec e **não** repete os critérios: eles já são da sessão.
- `/loop` é reconhecido como comando e o texto dele **não** vira entrada de turno.
- Um comando de usuário não pode sombrear `/loop`.
- Flag desconhecida em `/loop` para o comando, em vez de ser ignorada.
- `/loop` sem argumento mostra uso, e não abre sessão.
- Caminho de spec que sai do workspace é recusado, e a recusa nomeia o caminho.
- Caminho de spec dentro do workspace resolve contra ele, absoluto ou relativo.
- Spec nomeada é a definição de pronto da sessão; `done.toml` não é consultado.
- Spec que não dá para ler encerra a criação da sessão, sem cair no legado.
- Spec cujas tarefas não têm comando é zero critério e **não** é erro.
- A sessão informa quantos critérios carrega, e zero é resposta, não ausência.

**O que saiu daqui, e por quê.** Cinco invariantes descreviam a sessão que o
Passo 3 da `.i` vai criar — o servidor chamado uma vez, a sessão encerrada em
qualquer `StopReason`, `Protected` destacado durante o turno. Nenhuma tinha
teste, e nenhuma podia ter: a máquina que elas guardam não foi construída.
Ficaram na `.i`, ao lado do passo que as constrói.

A sexta era "`Progressed` é chamado entre ciclos, não pulado" — que o changelog
da família chamava de o teste mais importante desta spec. Ela sai por um motivo
diferente e melhor: **não há caminho novo a guardar**. A `DoneSet` é um valor,
e o motor não sabe de onde ela veio; é exatamente o que a RN-1 quer dizer com
fachada. Se o Passo 3 introduzir um caminho próprio de execução, é aí que a
invariante nasce — e a `agent-loop` já a guarda para o caminho que existe,
em `TestNoProgressEndsTheTurnAsIncomplete`.
