# Research: Distribuição e Atualização

> Fonte da verdade de negócio para como o dcode chega à máquina do usuário e como se mantém atualizado.
> Depende de: **ADR-01** (Go, binário estático único), **ADR-02** (o produto tem acesso a shell e filesystem).

## 1. Contexto

O dcode é um binário estático único — consequência direta da ADR-01. Isso torna a distribuição tecnicamente simples e desloca o problema para onde ele realmente é difícil: **confiança**.

O que se distribui aqui é um programa que executa comandos arbitrários e edita arquivos do usuário. O canal de distribuição é, portanto, um vetor de supply chain de alto valor. Um `curl | sh` sem verificação de assinatura entrega exatamente o que um atacante precisaria.

## 2. Fronteira de determinismo

**Regime: determinístico.**

Nada aqui é mediado por modelo. Verificação de assinatura, resolução de versão e troca de binário são regra explícita.

**Consequência para a revisão:** tudo é verificável por asserção. O `.p.spec.md` não tem seção de contratos comportamentais.

## 3. User stories

| # | Como | Quero | Para |
|---|---|---|---|
| US-1 | usuário novo | instalar com um comando | avaliar o projeto sem fricção |
| US-2 | usuário | saber que o binário que rodo é o que o projeto publicou | não confiar cegamente no canal |
| US-3 | usuário | atualizar quando **eu** decidir | a versão auditada hoje ser a que roda amanhã |
| US-4 | usuário corporativo | instalar sem acesso à internet no momento da instalação | ambiente restrito |

| US-6 | mantenedor | publicar uma versão sem passo manual | release não depender de memória de ninguém |

## 4. Regras de negócio

### RN-1 — Um artefato, quatro canais
Todos os canais entregam **o mesmo binário do mesmo release**. Nenhum canal compila localmente algo diferente do publicado.

| Canal | Público |
|---|---|
| `go install` | desenvolvedor Go |
| script de instalação | maioria |
| Homebrew tap | macOS |
| binário do GitHub Releases | corporativo, ar-gapped (US-4) |

### RN-2 — Todo release é assinado, e a instalação verifica
Assinatura e checksum publicados junto do artefato. O script de instalação **verifica antes de instalar**, e falha se a verificação falhar — nunca instala com aviso.

Esta é a regra mais importante do componente. Um agente de codificação com acesso a shell distribuído por canal não verificado é a definição de risco de supply chain.

`go install` é a exceção estrutural: a verificação ali é do módulo Go, pelo checksum database do próprio ecossistema. É garantia diferente, não ausência de garantia.

### RN-3 — Atualização nunca é automática
`dcode update` é comando explícito. O dcode **não** se atualiza sozinho, nem oferece opção para isso.

Um agente que troca o próprio binário sem consentimento anula qualquer auditoria: a versão revisada não é a que executa. O ganho de conveniência não paga essa perda.

### RN-4 — Aviso de versão é passivo, raro e local
No máximo uma verificação por dia, resultado em cache local, exibida como nota — nunca bloqueando. Falha de rede na verificação é silenciosa: nunca degrada a experiência de uso.

### RN-5 — Troca de binário é atômica e verificada
`dcode update` baixa, **verifica a assinatura**, e só então substitui — por escrita em arquivo temporário seguida de `rename`. Falha em qualquer etapa deixa a versão anterior intacta e funcional.

Binário parcialmente escrito é uma máquina sem dcode. Binário não verificado é pior.

### RN-6 — Versão é fixável e sempre reportável
`dcode --version` informa versão, commit e data de build. Instalação e atualização aceitam versão explícita (US-5).

### RN-7 — Release é reprodutível e automatizado
Publicar é disparar a automação a partir de uma tag. Nenhum passo manual, nenhuma máquina de desenvolvedor no caminho.

Passo manual em release é onde entra binário divergente — por acidente ou não.

### RN-8 — Auto-hospedagem é marco declarado do projeto

> **Marco de auto-hospedagem:** um pull request ao dcode escrito de ponta a ponta pelo dcode, aprovado na revisão e passando o gate de 90%, sem edição manual.

Não é aspiração de marketing: é a melhor eval que o projeto tem. A suíte de testes e o checklist de revisão do próprio produto viram função de aptidão.

**Ressalva registrada:** dogfooding enviesa o produto para workflows Go e CLI. Mitigação obrigatória — manter ao menos uma base de código de outra linguagem nas fixtures de eval. Sem isso, o agente fica excelente em Go e medíocre no resto sem ninguém perceber.

## 5. Fora de escopo

- Distribuição por gerenciador de pacote de distribuição Linux (apt, dnf, AUR).
- Imagem de container oficial.
- Canal de release de pré-lançamento com atualização automática.
- Telemetria de uso. O aviso de versão consulta a versão mais recente e nada mais.
