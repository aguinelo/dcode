# Planning: Distribuição e Atualização

> Contrato técnico. Use **EXATAMENTE** os nomes, campos e tipos definidos aqui.
> Regra de negócio em `202608072352-distribution.r.spec.md`.

## 1. Nível de estabilidade

**`stable` desde a primeira versão publicada** para três coisas: o **nome do binário** (`dcode`), o **formato do nome de artefato** e a **URL do script de instalação**. Quebrar qualquer um deles quebra instalação documentada em terceiros.

O resto (`internal/update`) é `experimental`.

## 2. Artefatos de release

Nome de artefato, formato fixo:

```
dcode_<versão>_<so>_<arch>.tar.gz      # darwin, linux
dcode_<versão>_windows_<arch>.zip
```

`<so>` ∈ `darwin`, `linux`, `windows` · `<arch>` ∈ `amd64`, `arm64`

Cada release publica também:

| Arquivo | Conteúdo |
|---|---|
| `checksums.txt` | SHA-256 de todos os artefatos |
| `checksums.txt.sig` | assinatura do arquivo de checksums |
| `checksums.txt.pem` | certificado da assinatura |

> Assina-se o **arquivo de checksums**, não cada artefato. Uma assinatura cobre o release inteiro e a verificação continua sendo por artefato individual, via SHA-256.

## 3. Instalação

```bash
# 1. Go
go install github.com/aguinelo/dcode/cmd/dcode@latest

# 2. script
curl -fsSL https://raw.githubusercontent.com/aguinelo/dcode/main/install.sh | sh

# 3. Homebrew
brew install aguinelo/tap/dcode

# 4. binário direto (US-4, ar-gapped)
#    baixar tar.gz + checksums.txt + .sig + .pem e verificar manualmente
```

### 3.1 Contrato do script de instalação

Ordem obrigatória, sem atalho:

1. Detecta SO e arquitetura; combinação não suportada aborta com a lista de suportadas.
2. Resolve a versão — `latest` ou `DCODE_VERSION`.
3. Baixa artefato e `checksums.txt`. Baixa `.sig` e `.pem` **apenas se houver cosign** — pedir uma assinatura que nenhuma ferramenta ali consegue ler só acrescenta um jeito de falhar por motivo que não é do usuário.
4. **Verifica a assinatura do `checksums.txt`, quando há cosign.** Falha aborta.
5. **Verifica o SHA-256 do artefato contra o digest que o próprio script carrega**, quando ele carrega um para aquele artefato. Falha aborta.
6. **Verifica o SHA-256 do artefato contra o `checksums.txt`.** Sempre. Falha aborta.
7. Extrai e instala em `DCODE_INSTALL_DIR`.
8. Confirma que o binário instalado executa `dcode --version`.

**Falha em 4, 5 ou 6 aborta e apaga o que baixou.** O que **não** aborta é a *ausência* do cosign.

As duas verificações são independentes, e exigir o cosign tornava a mais fraca condicional à mais forte: quem não o tinha ficava sem binário **e** sem verificação nenhuma — o pior resultado disponível, produzido pela regra escrita para evitá-lo. A linha que se sustenta não é "verificado ou nada", é **nunca não-verificado em silêncio**: o que não pôde ser conferido é dito na hora e repetido no fim, porque um install que termina numa linha de sucesso sem ressalva é lembrado como um sucesso sem ressalva.

### 3.2 O digest que o instalador carrega

O passo 5 existe porque o `checksums.txt` vem do **mesmo host** que o tarball. Sozinho ele pega download corrompido ou truncado; não pega release substituído, porque quem troca um troca o outro e o par continua coerente. Era a assinatura que cobria substituição — e ela é opcional desde que exigir cosign passou a deixar máquina comum sem binário e sem conferência.

Opcional não pode virar decorativa, e o que impede isso é o digest fixado. Entre `# BEGIN PINNED` e `# END PINNED`, o `scripts/installer.sh` escreve os SHA-256 dos quatro artefatos a partir do `checksums.txt` **já assinado**. O valor esperado passa então a viver no **histórico do git**: um asset de release pode ser substituído sem deixar rastro público, uma linha num arquivo versionado só muda por commit — visível, atribuído, revisável. Duas rotas independentes, e o atacante precisa das duas.

Três estados, e cada um tem uma resposta:

| Estado | O que faz |
|---|---|
| Carrega digest para este artefato | compara contra ele; divergência aborta, ainda que o `checksums.txt` concorde com o download |
| Carrega digests de **outro** release | avisa, aponta o `install.sh` daquele release, e cai no `checksums.txt` |
| Não carrega nenhum | cai no `checksums.txt`, **em silêncio** — avisar sobre um pino nunca aplicado ensina a ignorar a linha que importa |

### 3.3 O aviso tem o tamanho do que ficou por conferir

Sem cosign **e** sem digest fixado, nada ali cobre release substituído: o aviso ocupa quatro linhas e se repete na última, porque a rolagem de um `curl | sh` enterra o que apareceu no começo.

Sem cosign **com** digest fixado, substituição está coberta — é para isso que o digest existe. Repetir o aviso longo seria afirmar algo falso, e aviso que exagera é aviso que as pessoas aprendem a pular, inclusive na execução em que ele finalmente significa alguma coisa. Ali ele encolhe para duas linhas e não se repete.

O que **não** muda em nenhum dos dois: ele é dito. A linha que se sustenta continua sendo "nunca não-verificado em silêncio", e silêncio é o que nenhum dos casos produz.

> A separação é mais fraca que a do `uv`, que serve o instalador de um host e o artefato de outro. Sem domínio próprio, histórico do git contra asset de release é a melhor disponível, e dizer isso faz parte de tê-la.

O script não precisa de privilégio elevado se `DCODE_INSTALL_DIR` for gravável pelo usuário, que é o default.

## 4. Comando `update`

```go
// Package: internal/update

type Release struct {
    Version   string // semver, com "v"
    Artifacts map[string]Artifact // chave: "<so>_<arch>"
}

type Artifact struct {
    URL    string
    SHA256 string
}

type Updater interface {
    // Latest consulta a versão mais recente. Erro de rede NÃO é fatal
    // para o aviso passivo (RN-4).
    Latest(ctx context.Context) (Release, error)

    // Apply baixa, VERIFICA e troca o binário atomicamente (RN-5).
    Apply(ctx context.Context, r Release) error
}
```

### 4.1 Sequência de `Apply`

1. Baixa o artefato para diretório temporário **no mesmo sistema de arquivos** do binário atual — `rename` entre sistemas de arquivos não é atômico.
2. Verifica SHA-256 contra o release.
3. Verifica a assinatura do `checksums.txt`.
4. Extrai; confere que o binário executa `--version` e reporta a versão esperada.
5. `rename` sobre o binário atual.
6. Falha em qualquer etapa: apaga o temporário, deixa o atual intocado.

> Passo 4 antes do 5 é o que impede substituir um binário funcional por um que não roda naquela máquina.

### 4.1.1 Origem do binário

O binário declara **como foi produzido**, em variável própria injetada no link:

```go
const (
    SourceRelease = "release" // só o pipeline de release injeta
    SourceLocal   = "local"   // make install
)
```

Variável separada, e não formato inferido da versão: `Apply` recusa sobrescrever
binário que o pipeline não publicou, e decisão dessas não pode depender de
parsear string que qualquer um passa na linha de comando. Qualquer valor fora
dos dois é tratado como local — é a leitura que recusa.

**`Apply` recusa build local.** Um build da árvore de trabalho costuma estar *à
frente* da última tag, então instalar o release mais recente é downgrade
vestindo a palavra "atualizar". A recusa acontece **antes da consulta de rede**:
se a resposta é recusa de qualquer forma, perguntar ao GitHub primeiro gasta
ida-e-volta para reportar o motivo errado. `--force` levanta.

**Build local se identifica no texto da versão** — `0.0.0-dev+<commit>[.dirty]`
e a marca `local build` na saída de `--version`. Binário que se apresenta igual
a release publicado é como relato de bug vira hora perdida.

### 4.2 Aviso passivo de versão

```go
type VersionNotice struct {
    Current    string
    Latest     string
    CheckedAt  time.Time // persistido em disco, NUNCA no contexto do modelo
}
```

- No máximo uma consulta por `UpdateCheckInterval`, resultado em cache em `DCODE_STATE_DIR`.
- Erro de rede é silencioso: registra em `debug` e segue.
- Exibido como nota no cliente; jamais bloqueia (RN-4).
- **Nunca aplica nada.** O aviso é aviso (RN-3).

## 5. Pipeline de release

Disparado por tag `v*`, sem passo manual (RN-7):

1. `go test -race ./...` e gate de cobertura em matriz de macOS e Linux.
2. Build cruzado das quatro combinações, com `CGO_ENABLED=0`.
3. Injeta versão, commit e data via `-ldflags`.
4. Gera `checksums.txt`.
5. Assina com identidade efêmera OIDC, sem chave de longa duração em segredo de CI.
6. **Verifica a assinatura que acabou de produzir.**
7. **Fixa o `install.sh` nos digests deste release**, com `scripts/installer.sh`.
8. Gera a fórmula do Homebrew.
9. Publica o release com todos os artefatos, o `install.sh` fixado entre eles.
10. **Leva o `install.sh` fixado para a `main`**, com `scripts/publish-installer.sh`.
11. Atualiza a fórmula do Homebrew tap.

A ordem de 6 a 10 é o conteúdo, não a apresentação:

- **Fixar depois de verificar (7 > 6).** Digest fixado a partir de um `checksums.txt` que ninguém atestou é exatamente a falha que a fixação existe para impedir, reproduzida dentro do pipeline que a implementa.
- **Publicar depois de fixar (9 > 7).** Senão o asset publicado é o instalador sem pino.
- **Levar para a `main` depois de publicar (10 > 9).** A partir daí toda falha é irrecuperável no sentido que importa: o release já é público, e reprovar o job não despublica nada — pinta de vermelho um release que deu certo, que é o relatório sobre o qual ninguém consegue agir. Por isso os passos 10 e 11 saem com zero e avisam alto em toda condição recuperável.

O passo 10 precisa existir, e não basta o asset do passo 9: a URL que o README publica é `main/install.sh`. Um pino que fica só no release nunca alcança quem instala — e é ali que mora o argumento de segurança inteiro, porque asset de release se substitui sem rastro público e linha de arquivo versionado não.

> O commit do passo 10 tem assunto exato — `chore(release): pin the installer to vX.Y.Z` — e o `scripts/version.sh` o ignora. Sem isso, toda consulta de versão pós-release responderia "há commits desde a tag" com nada humano tendo mudado, e a derivação subiria PATCH sozinha. A isenção é do assunto exato, nunca do prefixo: isentar `chore(release):` inteiro daria a qualquer pessoa uma forma de não ser contada.

> Assinatura keyless por OIDC elimina a chave privada de longa duração — que seria o item de maior valor para um atacante no repositório inteiro.

## 6. Invariantes verificáveis

- O script de instalação aborta e não deixa resíduo quando a assinatura não confere.
- O script aborta quando o SHA-256 do artefato não confere.
- Sem cosign na máquina, o script confere o SHA-256 e instala.
- Sem cosign, o SHA-256 divergente continua abortando sem deixar resíduo.
- Sem cosign, o script diz que a assinatura não foi verificada e nomeia a ferramenta.
- Sem cosign, o script não baixa assinatura nem certificado.
- O instalador recusa artefato que diverge do digest que carrega, mesmo com o `checksums.txt` do release concordando com o download.
- O instalador instala o release ao qual foi fixado.
- Fixado num release e chamado para outro, avisa qual carrega e aponta o instalador daquele.
- Sem digest fixado nenhum, cai no `checksums.txt` sem reclamar.
- O gerador escreve o digest de toda plataforma publicada e recusa release ao qual falte uma.
- O pipeline fixa o instalador **depois** de verificar os checksums, publica **depois** de fixar, e escreve na `main` **depois** de publicar.
- O instalador fixado chega à branch que o README publica, com o assunto de commit que o `version.sh` ignora.
- Repositório inalcançável não reprova um release já publicado.
- Instalador fixado ausente reprova, em vez de deixar a `main` com os digests do release anterior.
- Republicar o mesmo instalador não é falha.
- O `version.sh` ignora o commit de pino do pipeline, e apenas o assunto exato dele.
- Com digest fixado conferido, o aviso não afirma que substituição ficou descoberta, e não se repete no fim.
- Sem digest fixado, o aviso afirma que substituição ficou descoberta e se repete no fim.
- SO ou arquitetura não suportada aborta listando as suportadas.
- `Apply` com artefato corrompido deixa o binário atual funcional e inalterado.
- `Apply` com binário novo que não executa deixa o atual funcional.
- `Apply` usa temporário no mesmo sistema de arquivos do alvo.
- Nenhum caminho de código aplica atualização sem chamada explícita a `update` (RN-3).
- A consulta de versão ocorre no máximo uma vez por `UpdateCheckInterval`.
- Falha de rede na consulta de versão não altera o código de saída de nenhum comando.
- `CheckedAt` nunca entra no contexto enviado ao modelo — violaria a ADR-03.
- `dcode --version` reporta versão, commit e data injetados no build.
- Build local reporta `local build`; release publicado não.
- `Apply` recusa build local sem `--force`, e a recusa vem antes de qualquer rede.
- O pipeline de release injeta `Source=release`; sem isso todo release publicado se recusaria a atualizar.
- Todos os canais entregam binário com o mesmo SHA-256 para a mesma versão e plataforma (RN-1).
